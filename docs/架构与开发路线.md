## 0. 项目一句话定位

**Sakura Coding Agent = Pi Runtime + Dynamic Planning + Multi-Agent Orchestration + Repository Intelligence + Isolated Workspace + Verification Loop + Experience/Skill Evolution。**

不做：

- Pi + 一堆插件 + 改名 Sakura
- 从零重写 Pi / Codex
- 为了“全自研”重造 Model SDK、Agent Loop、TUI、Shell、MCP SDK

重点解决 Pi Runtime 之上的软件工程问题：

1. **任务应该怎么动态拆解？**
2. **哪些任务应该并行，哪些存在依赖？**
3. **多个 Agent 如何协同而不是简单 spawn？**
4. **Agent 如何真正理解大型 Repository？**
5. **多个 Agent 如何隔离修改代码？**
6. **代码修改后如何强制验证并失败重规划？**
7. **历史成功/失败经验如何在后续任务中复用？**

# 2. 模块取舍：什么复用，什么自研

| 模块 | 策略 | 优先级 | 说明 |
|---|---|---:|---|
| Model Provider | 复用 Pi | - | 不重复造轮子 |
| 基础 Agent Loop | 复用 Pi | - | 需要读懂，不需要重写 |
| Session / Streaming | 复用 Pi | - | 基础设施 |
| Read / Write / Edit / Bash | 复用 Pi | - | 基础工具 |
| TUI / CLI 基础交互 | 尽量复用 Pi | - | 不作为卖点 |
| MCP Protocol | 复用现有实现 | P2 | Sakura 只做统一 Tool Adapter |
| Skills 加载 | 复用 + Router | P2 | 不做几百个 Skill |
| Subagent Spawn | 参考 `pi-subagents` | P0 | 只把它当底层执行能力 |
| **Dynamic Planning** | **自研** | **P0** | 核心 |
| **Task DAG / Replanning** | **自研** | **P0** | 核心 |
| **Multi-Agent Orchestrator** | **自研** | **P0** | 核心 |
| **Repository Intelligence** | **自研** | **P0** | 核心 |
| **Worktree Isolation** | **自研** | **P0** | 核心 |
| **Verification Loop** | **自研** | **P0** | 核心 |
| Sandbox / Guardrails | Pi + Sakura 增强 | P1 | 和 Worktree 配套 |
| Experience Engine | 自研 | P1 | 后期 |
| Skill Evolution | 自研 | P2 | 最后做 |
| Telemetry / Benchmark | 自研 | P1 | 项目证明材料 |

核心原则：

> **Pi 负责“一个 Agent 怎么运行”；Sakura 负责“一个软件工程任务怎么被理解、拆解、调度、执行、验证、复盘”。**

# 4. 核心数据模型

## 4.1 Task

```ts
export type TaskStatus =
  | "pending"
  | "ready"
  | "running"
  | "blocked"
  | "succeeded"
  | "failed"
  | "cancelled";

export type AgentRole =
  | "explorer"
  | "planner"
  | "architect"
  | "implementer"
  | "tester"
  | "reviewer"
  | "researcher";

export interface TaskNode {
  id: string;
  title: string;
  description: string;

  role: AgentRole;
  dependencies: string[];

  status: TaskStatus;
  priority: number;

  readScope?: string[];
  writeScope?: string[];

  verification?: VerificationSpec[];

  retryCount: number;
  maxRetries: number;

  result?: TaskResult;
}
```

## 4.2 TaskGraph

```ts
export interface TaskGraph {
  id: string;
  rootTask: string;
  version: number;

  nodes: Record<string, TaskNode>;
  edges: Array<{
    from: string;
    to: string;
  }>;

  createdAt: number;
  updatedAt: number;
}
```

要求：

- 必须是 DAG；
- 每个 dependency 必须存在；
- 写任务前尽可能确定 `writeScope`；
- Planner 输出后先做 schema validation，再进入执行；
- Replan 产生 `version + 1`，旧图保留到 trace。

# 5. 一次完整任务的运行时流程

```mermaid
sequenceDiagram
    participant U as User
    participant P as Planner
    participant R as Repo Intelligence
    participant O as Orchestrator
    participant W as Workspace Manager
    participant A as Agent
    participant V as Verifier
    participant E as Experience Engine

    U->>P: Coding Task
    P->>R: query symbols/files/tests
    R-->>P: repository context
    P->>P: build Task DAG
    P->>O: validated TaskGraph

    loop Ready Tasks
        O->>O: resolve dependencies
        O->>W: create isolated workspace
        W-->>O: worktree path
        O->>A: execute task + scoped context
        A-->>O: result + diff + trace
    end

    O->>V: verify integrated result
    V->>V: lint/typecheck/test/build/review

    alt Verification Failed
        V-->>P: failure evidence
        P->>P: replan / patch DAG
        P->>O: TaskGraph vNext
    else Verification Passed
        V-->>O: pass
        O-->>U: final result
        O->>E: trace + task + successful diff
        E->>E: extract reusable experience
    end
```

# 6. Dynamic Planning

Planning 和 Orchestrator 必须拆开：

```text
Planner      = 决定做什么
Orchestrator = 决定谁做、什么时候做、在哪里做
```

## 6.1 Task Analyzer

先判断任务复杂度，而不是任何任务都启动多个 Agent。

```ts
interface TaskAnalysis {
  type: "edit" | "bugfix" | "feature" | "refactor" | "research";
  complexity: "small" | "medium" | "large";
  likelyFiles: string[];
  requiresRepoExploration: boolean;
  requiresParallelism: boolean;
  requiresArchitecture: boolean;
  risk: "low" | "medium" | "high";
}
```

建议规则：

```text
README typo
→ Edit → Verify

单文件 Bug
→ Explore → Implement → Verify

跨模块 Bug
→ Explore A ┐
            ├→ Diagnose → Implement → Test → Review
  Explore B ┘

大型 Feature
→ 多路 Explore → Architect → 多路 Implement → Integration → Verify
```

## 6.2 Planner 输入

```text
User Task
+ Repo Intelligence
+ Current Git State
+ Relevant Skills
+ Retrieved Experience
+ Tool Availability
+ Execution Policy
```

## 6.3 Planner 输出

只允许输出结构化 `TaskGraph`，不要让 Scheduler 解析自由文本。

## 6.4 Replanning

触发条件：

- 测试失败且不是简单一次性修复；
- 发现新的依赖模块；
- 原任务节点不可执行；
- Agent 返回 `needs_replan`；
- Worktree 合并冲突暴露错误任务边界；
- 连续 retry 超限。

```mermaid
flowchart LR
    A[Plan v1] --> B[Execute]
    B --> C[Verify]
    C -->|pass| D[Complete]
    C -->|fail| E[Failure Classifier]
    E --> F{local fix?}
    F -->|yes| G[Retry Task]
    G --> C
    F -->|no| H[Replanner]
    H --> I[TaskGraph v2]
    I --> B
```

# 7. Multi-Agent Orchestrator

不要把 Orchestrator 写成 `Promise.all(spawnAgent(...))`。

## 7.1 内部组件

```mermaid
flowchart TB
    DAG[Task DAG] --> DR[Dependency Resolver]
    DR --> RQ[Ready Queue]
    RQ --> SCH[Scheduler]
    SCH --> CC[Concurrency Controller]
    CC --> AR[Agent Runner]
    AR --> AL[Agent Lifecycle]
    AR --> WM[Workspace Manager]
    AR --> RA[Result Aggregator]
    RA --> DAG
```

## 7.2 Scheduler 最小算法

伪代码：

```ts
while (!graphFinished(graph)) {
  const ready = getReadyTasks(graph);

  const runnable = ready
    .filter(task => !hasWriteConflict(task, runningTasks))
    .slice(0, concurrencyLimit);

  await Promise.all(
    runnable.map(task => runTask(task))
  );

  updateGraphFromResults();

  if (shouldReplan()) {
    graph = await replanner.replan(graph, failures);
  }
}
```

## 7.3 不是什么任务都并行

并行条件至少包括：

```text
dependencies 满足
AND writeScope 不冲突
AND concurrency slot 可用
AND 资源预算允许
```

例如：

```text
explore-auth ─┐
              ├── design-auth
explore-db ───┘

design-auth ──┬── implement-auth
              └── implement-tests

implement-auth ──┐
                 ├── integration-test
implement-tests ─┘
```

# 8. Agent 生命周期

```mermaid
stateDiagram-v2
    [*] --> Created
    Created --> Preparing
    Preparing --> Running
    Running --> Succeeded
    Running --> Failed
    Running --> WaitingApproval
    WaitingApproval --> Running
    Failed --> Retrying
    Retrying --> Running
    Failed --> Cancelled
    Succeeded --> Collected
    Collected --> Cleaned
    Cancelled --> Cleaned
    Cleaned --> [*]
```

建议 AgentRunner 对 Pi 暴露一个很薄的适配层：

```ts
interface AgentRunner {

}

interface AgentRunInput {
  agentId: string;
  role: AgentRole;
  task: TaskNode;
  workspacePath: string;
  context: ContextBundle;
  allowedTools: string[];

interface AgentRunResult {
  status: "success" | "failure" | "needs_replan";
  summary: string;
  changedFiles: string[];

  evidence: string[];
  tokenUsage?: number;
  toolCalls?: number;
}
```

这样未来 Pi 内部 API 变化时，只改 Adapter，不污染 Sakura 核心逻辑。

# 9. Repository Intelligence

这一模块不要和 Pi 自带的 Context Compression 混为一谈。

```text
Pi Context Compression：
“上下文已经太长，怎么压缩？”

“当前任务真正需要理解 Repository 的哪些结构？”
```

# 10. Context Builder 与 Token Budget

Repo Intelligence 负责“找什么”，Context Builder 负责“给 Agent 多少”。

```mermaid
flowchart TB
    TASK[Task] --> RET[Repo Retrieval]
    RET --> CAND[Candidate Context]
    CAND --> RANK[Ranking]
    RANK --> BUDGET[Token Budget]
    BUDGET --> BUNDLE[Context Bundle]

    HISTORY[History] --> BUDGET
    SKILLS[Skills] --> BUDGET
    EXP[Experience] --> BUDGET
    DIFF[Current Diff] --> BUDGET
```

示例预算：

```text
Total                 64K
├── System             5K
├── Task / Plan         4K
├── Skills              3K
├── Experience          3K
├── Repository Code    30K
├── Tool Results        7K
├── History             8K
└── Reserve             4K
```

超限顺序：

1. 移除低相关候选文件；
2. 去掉重复代码片段；
3. 压缩旧 Tool Result；
4. 压缩旧 History；
5. 保留当前任务、当前 Diff、关键依赖和测试；
6. 不要为了自研而替换 Pi 已经做得好的基础 context compaction。

# 11. Worktree Isolation

这是 Multi-Agent 真正可工程化的关键。

```mermaid
flowchart TB
    MAIN[Main Repository] --> WM[Workspace Manager]
    WM --> WA[Worktree A<br/>Agent A]
    WM --> WB[Worktree B<br/>Agent B]
    WM --> WC[Worktree C<br/>Agent C]

    WA --> DA[Diff A]
    WB --> DB[Diff B]
    WC --> DC[Diff C]

    DA --> CONFLICT[Conflict Detector]
    DB --> CONFLICT
    DC --> CONFLICT

    CONFLICT --> INTEGRATE[Integration Workspace]
    INTEGRATE --> VERIFY[Full Verification]
    VERIFY --> MERGE[Final Merge]
```

## 11.1 AgentSession

```ts
interface AgentSession {
  agentId: string;

  branch: string;
  worktreePath: string;

  baseCommit: string;

  changedFiles: string[];
  diff?: string;

  startedAt: number;
  endedAt?: number;
}
```

## 11.2 WorkspaceManager

```ts
interface WorkspaceManager {
  createWorkspace(task: TaskNode): Promise<AgentSession>;
  runInWorkspace(session: AgentSession, command: string): Promise<CommandResult>;
```

第一版实现优先级：

```text
P0 create worktree

P0 cleanup

```

# 12. Sandbox / Permission

Worktree 解决代码隔离，但不等于 Sandbox。

第一版可以先做 Policy Layer：

```text
workspace 内 read       allow
workspace 内 write      allow
workspace 外 read       configurable
workspace 外 write      deny
git push                approval
危险 shell              approval / deny
网络访问                 configurable
删除大量文件             approval
修改密钥/配置目录         deny / approval
```

接口：

```ts
interface ToolPolicy {
  evaluate(action: ToolAction): PolicyDecision;
}

type PolicyDecision =
  | { type: "allow" }
  | { type: "deny"; reason: string }
  | { type: "approval"; reason: string };
```

不要第一版就自己实现容器级 OS Sandbox。先把 Agent 工作目录和危险行为约束清楚，后续再接 Docker / container runtime。

# 13. Verification-driven Workflow

项目必须坚持：

> **No verification, no completion.**

```mermaid
flowchart LR
    I[Implement] --> D[Inspect Diff]
    D --> L[Lint]
    L --> T[Typecheck]
    T --> UT[Unit Test]
    UT --> B[Build]
    B --> R[Review]
    R --> P{Pass?}
    P -->|yes| C[Complete]
    P -->|no| F[Failure Evidence]
    F --> X[Diagnose / Fix / Replan]
    X --> I
```

不是所有项目都有全部命令，因此需要 `CommandDetector`：

```text
package.json
pyproject.toml
Makefile
Cargo.toml
go.mod
CI config
README / CONTRIBUTING
```

得到：

```ts
interface VerificationPlan {
  lint?: string[];
  typecheck?: string[];
  test?: string[];
  build?: string[];
  custom?: string[];
}
```

最终 `VerificationResult` 必须包含证据：

```ts
interface VerificationResult {
  passed: boolean;
  steps: Array<{
    command: string;
    exitCode: number;
    durationMs: number;
    stdoutTail: string;
    stderrTail: string;
  }>;
  reviewedDiff: boolean;
  failures: VerificationFailure[];
}
```

Agent 最终不能只说“应该修好了”。


降级：

```text

maxReplans = 2~3
```

## 风险 5：Skill Evolution 太玄学

降级：

```text
只做 Experience Retrieval
Skill Evolution 放 v1.1
```

# 34. Definition of Done

一个功能只有满足下面条件才算完成：

```text
[ ] 有明确 interface / schema
[ ] 有 unit test
[ ] 有至少一个 integration test
[ ] Trace 能记录关键事件
[ ] 错误有结构化返回
[ ] 文档说明输入/输出
[ ] 不依赖人工观察 LLM 文本判断成功
```

一个 Coding Task 只有满足：

```text
[ ] 代码修改完成
[ ] diff 已检查
[ ] 可用 lint 已执行
[ ] 可用 typecheck 已执行
[ ] 可用 tests 已执行
[ ] 可用 build 已执行
[ ] 失败已经修复或明确报告
[ ] 最终 evidence 已记录
```

才允许进入 `COMPLETE`。

# 35. 最终实施顺序

```text
Pi Runtime Integration
        ↓
PiAgentAdapter
        ↓
Trace / Telemetry
        ↓
Single-Agent Coding Workflow
        ↓
Verification Loop
        ↓
TaskGraph / Dynamic Planning
        ↓
Multi-Agent Scheduler
        ↓
Repository Intelligence
        ↓
Context Builder
        ↓
Git Worktree Isolation
        ↓
Integration / Conflict Handling
        ↓
Experience Retrieval
        ↓
Skill Evolution
        ↓
Benchmark / Ablation
        ↓
Sakura v1.0
```

最关键的一点：

> **不要同时开发五个“大模块”。先让每一层都有可运行的端到端版本，再往下一层加能力。**

第一个真正值得提交的版本不是“支持 MCP/Skills”，而是：

```text
User Task
→ Sakura
→ 修改真实代码
→ 自动验证
→ 留下完整 Trace
→ 给出可检查的 Diff 和 Evidence
```

之后再逐步证明：

```text
Dynamic Planning 是否减少无意义 Agent？
Multi-Agent 是否提高复杂任务完成能力？
Repo Intelligence 是否减少无关上下文？
Worktree 是否让并行修改真正安全？
Experience Retrieval 是否减少重复失败？
```

这些问题最终都应该由 **Benchmark 数据**回答，而不是 README 文案回答。
